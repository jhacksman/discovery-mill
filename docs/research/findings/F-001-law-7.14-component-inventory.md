## Implications for Discovery Mill (PROPOSED)

- Reference product separates *UI/case shell* from *processing services* (import, OCR, print/render, text extraction, dedup, near-dup). Discovery Mill should adopt the same separation with a job queue, but with open engines: LibreOffice/unoserver or equivalent for Office→PDF, pdfium/MuPDF/Ghostscript for PDF→TIFF, Tesseract for OCR, libmagic/Apache Tika/Siegfried for file identification, SQLite for the case store.
- LAW's OCR path is Tesseract-backed in 7.14 (via VintaSoft); OCR quality parity with Tesseract 5 is therefore an achievable target (INFERRED).
- Visual FoxPro ODBC and SQL Server dependencies mean legacy LAW cases are *not* a portable interchange format; interoperability must be at the load-file level (DAT/OPT/LFP/DII), not the case database.

## Limitations

- Static inventory only; no behaviour was executed. Component roles are inferred from file descriptions and names.
- MSI `File`-table parsing with the ad-hoc reader was unreliable for names/sizes; inventory was taken from the extracted cab members' own PE version resources instead.
- REA `inspect-pe-certificates` could not run on the 557 MB bundle (512 MiB cap); signer data came from a custom PKCS#7 parse of the security directory.
